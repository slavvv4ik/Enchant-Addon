# Mana Machines — исправление ошибок запуска (Bedrock 1.26.x)

Исходники аддона лежат в `src/` (распакованы из исходного `.mcaddon`), сборка — `python3 build.py`.

## Что было сломано и что исправлено

### 1. `Could not find export 'Enchantment' in module '@minecraft/server'`

В `@minecraft/server` 2.x (у вас в манифесте `2.11.0`) **`Enchantment` — это только
TypeScript-интерфейс**, а не runtime-класс. Импортировать его как значение и делать
`new Enchantment(type, level)` нельзя — движок падает ещё до выполнения скрипта.

Исправлено в `src/Mana_Machines_BP/scripts/main.js`:

- убран `Enchantment` из импорта;
- все `new Enchantment(type, level)` заменены на обычный объект `{ type, level }`,
  который и принимает `ItemEnchantableComponent.addEnchantment()`;
- добавлен хелпер `enchantmentType(id)` — пробует ID и с префиксом `minecraft:`, и без
  него, а `normalizeEnchantId()` приводит ID к единому виду при сравнении;
- перед применением зачарования вызывается `canAddEnchantment()`.

### 2. `1.20+ Recipes require unlock data`

Начиная с формата рецептов 1.20.10 каждый рецепт обязан содержать поле `unlock`
(условие открытия в книге рецептов). В трёх рецептах его не было.

Исправлено в `recipes/anvil.json`, `recipes/condenser.json`, `recipes/fusion.json` —
добавлено:

```json
"unlock": [ { "item": "minecraft:obsidian" } ]
```

Рецепт появляется в книге, как только игрок получает обсидиан. Сам крафт работает
и без открытия, если не включён геймрул `doLimitedCrafting`.

### 3. Попутно исправленные скрытые ошибки API

- **`blockContainerOpened`**: событие не содержит `event.container` / `event.player`.
  Контейнер теперь берётся из `event.block.getComponent("minecraft:inventory").container`,
  а игрок — из `event.openSource.entity`.
- **`blockExplode`**: событие приходит на каждый блок и не содержит массива `event.blocks`.
  Тип разрушенного блока берётся из `event.explodedBlockPermutation.type.id`.
- **Витринные предметы**: компонентов `minecraft:pickup_delay` и `minecraft:physics`
  в Script API нет. Подбор запрещён через `beforeEvents.entityItemPickup`, а от падения
  предметы возвращаются к якорю (`stabilizeDisplays`).
- `playerBreakBlock`: убран несуществующий fallback `brokenBlockPermutation.typeId`.

### 4. v1.0.4: мана отображается, но машины не реагируют на клик

Причина: кастомные блоки без interact-компонента не вызывают
`playerInteractWithBlock`, поэтому обработчики машин никогда не запускались.

Исправлено:

- блоки переведены на формат `1.21.90` и получили Custom Component V2
  `mana:machine_interaction`;
- компонент регистрируется через `system.beforeEvents.startup` и обрабатывает
  `onPlayerInteract` / `onPlace`;
- добавлена защита от двойного срабатывания одного клика;
- стандартное использование предмета по машине отменяется, чтобы ведро воды или
  блок в руке не срабатывали вместо взаимодействия;
- зелья маны получили `minecraft:use_animation: drink`, чтобы корректно завершать
  использование и восстанавливать ману;
- поиск типа зачарования стал устойчивее к ID с префиксом `minecraft:` и без него.

### 5. v1.0.5: крафт из дропа, лимиты уровней и посадочные места предметов

#### 5.1 Лазурит + золотой самородок + камень на земле не давали манакамень

Старый код пытался прочитать компонент предмета прямо в `entitySpawn` (там его
ещё нет), ждал один тик и блокировал расчёт по целой клетке `location`. Плюс
`entity.kill()` для предметных сущностей возвращает `false` — дроп не удалялся.

Теперь:

- при выбросе ингредиента проверка планируется через 2 тика, а каждые 10 тиков
  рядом с игроками (радиус 10) сканируются уже существующие дроп-сущности;
- все три ингредиента ищутся по **расстоянию** (кластер ~2 блока по горизонтали,
  ±1 блок по высоте), а не по совпадению клетки;
- ингредиенты проверяются **до** списания: неполный набор никогда не тратится;
- удаление идёт через `entity.remove()` (не `kill()`), из стака расходуется одна
  единица, остаток возвращается дропом;
- если удалось удалить не всё или не создался результат, ингредиенты
  возвращаются — крафт отменяется целиком;
- из одного набора за проход получается ровно один камень: иначе 3+3+3
  превратились бы в три камня.

#### 5.2 Слияние поднимало уровень выше ванильного максимума

Две причины:

1. Динамические свойства (`dynamic properties`) в Bedrock работают **только на
   нестакуемых предметах**. Сформированные камни были `max_stack_size: 64`,
   `setDynamicProperty("mana:level", …)` выбрасывал исключение, а пустой
   `catch {}` тихо оставлял уровень I. Теперь у всех 30 `stone_*.json` стоит
   `max_stack_size: 1`, а ошибка записи уровня больше не скрывается.
2. Предел брался только из внутренней таблицы (`info.max`). Теперь уровень
   ограничивается `min(таблица, EnchantmentType.maxLevel)` из реестра игры,
   то есть ванильным максимумом конкретного зачарования.

Итог: `II + II → III` работает, `IV + IV → V` для «Остроты» работает, а `V + V`
отклоняется с сообщением «Максимальный уровень этого зачарования: V». Для
зачарований с максимумом II («Заговор огня», «Откидывание», «Ледоход»,
«Отбрасывание») `II + II` не проходит; для максимума I («Бесконечность»,
«Починка», «Шёлковое касание» и др.) слияние не даёт ничего. Уровень,
превышающий максимум, обрезается. Камни, созданные в v1.0.4 (уровень потерян,
но сохранён в названии), восстанавливают уровень по римской цифре в `nameTag`.

#### 5.3 Предметы висели над блоком, а не на посадочных местах

Раньше все витринные предметы спавнились в одной точке `y + 1.25` со сдвигом
±0.22 по X. Теперь у каждой машины свои места, посчитанные по геометрии моделей
(16 px = 1 блок; **X геометрии блока инвертирован к мировому X**):

| Машина | Место в модели (px) | Смещение в мире |
| --- | --- | --- |
| Конденсатор (чаша) | 0; 8.85; 0 | центр, `y + 0.678` |
| Наковальня (сигил) | 0; 16.5; 0 | центр, `y + 1.156` |
| Слияние, левый слот | −5; 11; 0 | `x + 0.8125`, `y + 0.8125` |
| Слияние, правый слот | +5; 11; 0 | `x + 0.1875`, `y + 0.8125` |

Дополнительно витринный предмет записывает `mana:display_machine`,
`mana:display_slot` и `mana:display_version`: при обновлении пака старые
витрины удаляются по владельцу, а у уже поставленных машин якоря переносятся
на новые координаты без переустановки блока. Смещение `+0.125` по Y —
компенсация высоты спрайта предмета (≈2 px), она может потребовать небольшой
подстройки в живом мире.

### 6. v1.0.6: полоса маны над полосой опыта

Мана игрока раньше показывалась только текстом в экшен-баре. Теперь в HUD
добавлена отдельная полоса — над ванильной полосой опыта, по её ширине.

**Как это работает.** Добавить элемент в HUD можно только из ресурс-пака
(`RP/ui/hud_screen.json`), а JSON UI не умеет читать скриптовые данные.
Поэтому значение передаётся единственным доступным каналом — строкой
заголовка (`#hud_title_text_string`), которую JSON UI читает биндингом:

- скрипт публикует `player.onScreenDisplay.setTitle("MM:<0..1000>", …)`;
  число — доля маны в тысячных, при активном восстановлении прибавляется
  `10000` (полоса рисуется другой текстурой);
- публикация идёт только при изменении значения, плюс принудительный
  heartbeat раз в 60 тиков на случай, если движок очистил строку;
- в RP полоса сделана по образцу ванильной полосы опыта: изображение с
  `clip_direction: left` и биндингом значения в `#clip_ratio`;
- свой же служебный заголовок скрыт: к ванильным `title` и `title_background`
  добавлен биндинг видимости `((#text - 'MM:') = #text)` — то есть «показывать
  только то, что не начинается с нашего маркера».

Добавленные файлы:

- `RP/ui/hud_screen.json` — панель `mana_machines.mana_bar_panel` (182×5 px,
  как ванильная полоса опыта), вставляется в `root_panel` через `modifications`,
  а не заменой файла целиком;
- `RP/textures/ui/mana_bar_empty.png`, `mana_bar_fill.png`,
  `mana_bar_fill_regen.png` — пустая полоса, заливка и заливка при
  ускоренном восстановлении.

**Калибровка.** Положение полосы задаётся переменной `$mana_bar_offset` в
`RP/ui/hud_screen.json` (сейчас `[0, -46]`, то есть 46 px выше нижнего края
экрана). Если полоса оказалась слишком высоко/низко или перекрывает полосу
опыта — меняется только это число.

**Ограничения.**

- Полоса не привязана к полосе опыта: когда опыта нет, ванильная полоса
  скрывается, а полоса маны остаётся на своём месте (прыгать не будет).
- Любой другой HUD-пак, который тоже меняет `hud_screen.json`, может
  перекрыть или сдвинуть панель — при конфликте наш пак должен быть ниже
  чужих в списке ресурсов.
- Обновления игры меняют структуру HUD; панель вставлена через
  `modifications` (рекомендуемая практика), но после крупного апдейта
  положение стоит проверить.
- Раскладка на тач-устройствах отличается: смещение, подобранное на ПК,
  на телефоне может потребовать правки.
- Служебный заголовок занимает канал title: чужие заголовки показываются
  как обычно, но наш скрыт.

### 7. v1.0.7: полоса не отображалась — исправлен мердж HUD

Первая сборка полосы (v1.0.6) не показывалась вовсе: по скриншотам с телефона
в HUD не было ни одного пикселя текстур полосы. Причины устранены:

- **Свой `namespace` в merge-файле.** В `ui/hud_screen.json` был объявлен
  `"namespace": "mana_machines"`, из-за чего блок `root_panel` создавал новый
  элемент вместо правки ванильного `hud.root_panel`, и вставка не применялась.
  Namespace убран, панель описана целиком внутри `modifications`.
- **Наследование через `@` и `$`-переменные.** Элементы `mana_bar_fill@...`
  и `$mana_bar_offset` в поддеревьях из `modifications` не разрешались
  (`$`-переменные в таких поддеревьях движок отбрасывает). Осталось только
 inline-описание и литеральные значения.
- **Позиция от низа экрана.** Замер по скриншоту: полоса опыта на Pocket
  занимает 25–32 UI px над низом, а смещение было `-46`. Теперь полоса
  привязана к самой ванильной полосе опыта (`anchor_from: bottom_middle` →
  `anchor_to: top_middle`, `offset [0, -2]`) и вставляется сразу в три места:
  `resizing_xp_bar_with_hotbar` и `resizing_hotbar_no_xp_bar` обычной
  раскладки и `resizing_xp_bar_with_hotbar` карманной. Ширина — `100%` от
  полосы опыта, поэтому совпадает с ней на любом GUI scale.
- **Лишний `nineslice_size`** убрал: он не нужен для этих текстур.

В этой сборке пустая полоса сделана **ярко-красной специально для
диагностики**: если красная полоса появилась — панель рендерится, и следующим
шагом возвращаю тёмный стиль и проверяю заливку. Если красной полосы нет —
нужен лог контента (Настройки → Автор → Лог контента) и проверка, что в мире активен
именно ресурспак из нового `.mcaddon`.

### 8. v1.0.8: вставка только в root_panel, явные пиксели

В v1.0.7 полоса вставлялась внутрь ванильной `resizing_xp_bar_with_hotbar`,
чтобы inherit ширину и положение полосы опыта. Модификация применилась (это
было видно по съехавшей цифре уровня), но самой полосы не было: у родителя
ширина задана как `100%c`, то есть **по содержимому**, а дочерняя ширина
`100%` в таком родителе даёт круговую зависимость — панель схлопывалась в ноль
и заодно ломала раскладку родителя (цифра опыта уехала в левый край).

Теперь:

- вставка идёт только в `root_panel` — это обычная полноэкранная панель с
  фиксированной геометрией, там проценты безопасны;
- размер панели задан явными пикселями `[182, 5]` (182 px — ширина ванильной
  полосы опыта), а не `100%c`;
- положение — `offset [0, -35]` от низа экрана: по замеру скриншота полоса
  опыта на Pocket занимает 25–32 UI px над низом, значит зазор выходит ~3 px.
  Значение одно и правится в одном месте;
- вставку внутрь `exp_progress_bar_and_hotbar*` теперь запрещает тест.

### 9. v1.0.9: полоса выше сердец и голода, возвращён обычный вид

Полоса заработала (рендерится, заливка меняется, зелье регенерации
перекрашивает её в фиолетовый), но перекрывала сердца и голод. Замер
скриншота в пикселях от низа экрана (Pocket, масштаб ≈5):

| Элемент | Занимает, px от низа |
| --- | --- |
| Хотбар | 8–117 |
| Полоса опыта | 130–154 |
| Сердца и голод | 171–201 |
| Полоса маны (v1.0.8) | 174–201 — перекрывала сердца |
| Полоса маны (v1.0.9) | 218–243 — выше сердец, зазор ≈4 UI px |

### 11. v1.0.11: сердца и голод всё-таки переехали, цифра опыта убрана из-под полосы, заливка больше не застывает

Три правки по результатам проверки v1.0.10.

**1. Сердца и голод не переехали — якорь `where` не тот.** Ванильные сердца,
броня, голод, пузыри и сердца лошади — это инстансы (`heart_rend@heart_renderer`
и т. д.) внутри `centered_gui_elements_at_bottom_middle` / `..._touch`, у них
задано скалярное `offset`. Править скаляр можно операцией `replace`
c `array_name: "controls"`, но якорь `where: {control_name: ...}` в клиенте не
сработал: полоса встала правильно, а сердца остались на месте. Поэтому базовые
элементы (`heart_renderer`, `hunger_renderer`, `armor_renderer`,
`bubbles_renderer`, `horse_heart_renderer`, `progress_text_label`) скрываются
дополнительным биндингом `#visible`, а вместо них вставляются свои копии —
только операции `insert_back`, которые уже проверены. Смещения: -40 → **-47**
(на 7 UI px выше), броня едет вместе с сердцами, пузыри и сердца лошади —
соответственно.

**2. Цифра уровня опыта убрана из-под полосы.** Ванильная подпись
`progress_text_label` стоит по центру над полосой опыта — ровно там, где
теперь полоса маны. Своя копия получила `offset [-107, 5]`: цифра опускается
на уровень полосы опыта и уходит влево от неё. В обычной (не карманной)
раскладке родитель размера `100%c`, поэтому туда копия ставится без смещения,
как в ванили.

**3. Заливка больше не зависит от деления в JSON UI.** Значение публикуется
шагом 0..50 (+1000 при ускоренном восстановлении), а в UI заливка — это 50
картинок шириной 2 %, 4 %, …, 100 %, у каждой видимость `(#mana_value = N)`.
Ни деления, ни дробей, ни `#clip_ratio`. Плюс найдена причина «полоса тёмная
при полной мане»: движок обновляет `#hud_title_text_string`, только когда
строка заголовка меняется, поэтому на постоянном значении полоса застывала
пустой. К каждой публикации добавлен меняющийся ведущий ноль (`MM:25` /
`MM:025`) — число от него не меняется, а строка другая.

Если полоса по-прежнему будет вести себя странно, правится одно место:
`publishManaBar` в `main.js` (что публикуем) и блок `mana_bar_fill_*`
в `RP/ui/hud_screen.json` (как это рисуется).

### 12. v1.0.12: оригиналы сердец и голода скрыты, цифра уровня перенесена

Полоса маны больше не меняется — она встала как надо. Остались две правки.

**1. Оригиналы сердец и голода не пропали.** Скрытие биндингом вида
`{"binding_name": "(0)", "binding_name_override": "#visible"}` в клиенте не
сработало: копии появились там, где нужно, а ванильные сердца и голод остались
на месте и перекрывали полосу. Скрывать стало тем же приёмом, что уже проверен
на заливке полосы: читаем `#hud_title_text_string`, снимаем маркер и сравниваем
число со значением `99999`, которого скрипт не публикует никогда — значит
`#visible` всегда ложь. Наши копии от этого канала не зависят, так что сердца
не пропадут, даже если заголовок окажется пустым.

**2. Цифра уровня не переехала.** Копия подписи вставлялась в
`exp_progress_bar_and_hotbar_pocket` — этой группы на экране не оказалось.
Переносить копию внутрь группы опыта нельзя в принципе: у родителей там размер
`100%c` (по содержимому), и ребёнок со смещением меняет границы содержимого —
группа опыта и хотбар уезжают (это уже случалось в v1.0.7). Поэтому цифра
теперь живёт в `root_panel`, рядом с полосой маны, и привязана к низу экрана:
`offset [-107, 26]` — полоса опыта занимает 26.3..31.1 UI px, низ подписи на
26 UI px даёт центр ровно на уровне полосы, а по горизонтали цифра уходит
влево от неё. Группы опыта файл больше не трогает вовсе.

### 13. v1.0.13: найдено, почему не применялись правки сердец и цифры уровня

**Причина.** Модификация **самого наследуемого элемента** (`"heart_renderer"`,
`"progress_text_label"`) до инстансов `heart_rend@heart_renderer` не доходит —
проверено дважды, в v1.0.11 и v1.0.12. Работает только путь вида
**«элемент/ребёнок»**: так у нас уже применялись вставка в `root_panel` и
скрытие служебного заголовка.

Что сделано:

- **Сердца, броня, голод, пузыри.** Оригиналы правятся на месте — `replace` по
  `array_name: "controls"` с якорем `control_name` (без `where`, который в
  v1.0.10 не сработал): `-40` → `-47`. Дополнительно те же инстансы скрываются
  биндингом по пути `centered_gui_elements_at_bottom_middle_touch/heart_rend@heart_renderer`
  — если `replace` не сработает, сработает скрытие. Вставленные копии остаются:
  если сработают оба механизма, они просто накладываются друг на друга.
- **Цифра уровня.** Две ошибки. Первая: копия вставлялась в
  `exp_progress_bar_and_hotbar_pocket`, а активна другая группа. Вторая и
  главная — знак: `offset [-107, 26]` уводил подпись за нижний край экрана
  (минус по Y — это вверх, как у полосы маны с её `-32`). Теперь `[-107, -26]`:
  низ подписи на 26 UI px выше низа экрана, её центр — ровно на уровне полосы
  опыта, по горизонтали она левее её.
- **Оригинал цифры** убирается `replace` со смещением `[0, -500]` — только по
  вертикали: у родителя ширина `100%c`, и сдвиг по X увёл бы всю группу опыта и
  хотбар (это уже ломалось в v1.0.7). Плюс тот же биндинг-скрытие по пути.

### 14. v1.0.14: возврат к рабочему состоянию, полоса выше сердец и голода

**Что случилось в v1.0.13.** Файл `hud_screen.json` был отклонён движком
целиком: весь наш HUD пропал, а служебный заголовок, который RP обычно скрывает,
стал виден посреди экрана как `MM:050` / `MM:50`. Причина — правки ванильных
инстансов: модификация по пути с `@`
(`.../heart_rend@heart_renderer`) и операция `replace` с якорем `control_name`.
Ошибка ресурспака приводит к тому, что не применяется весь файл, поэтому
прежняя рабочая часть тоже перестала действовать.

**Что сделано.** Файл опять правит ровно три места — и только те, которые
проверены в клиенте:

- вставка полосы маны в `root_panel` (`insert_back`);
- скрытие служебного заголовка и его подложки (`insert_back` в `bindings`).

Больше никаких правок ванильных контролов: ни базовых элементов (до инстансов
`@heart_renderer` правки не доходят), ни путей с `@`, ни `replace`.

**Куда делась полоса.** Оригинальные сердца и голод в карманной раскладке
занимают 163..201 px от низа экрана и сдвинуть их нельзя, поэтому полоса
ставится выше них: `offset [0, -44]` — низ на 218 px, зазор до сердец около
17 px. Так полоса не перекрывает ни сердца, ни голод, ни цифру уровня опыта.

### Что известно про модификации HUD (итог пяти попыток)

| Что пробовали | Результат |
| --- | --- |
| Вставка в `root_panel` через `insert_back` | работает |
| Вставка биндинга по пути `hud_title_text/title_frame/title` | работает |
| Вставка контролов в `centered_gui_elements_at_bottom_middle_touch` | работает |
| Правка базового элемента (`heart_renderer`, `progress_text_label`) | до инстансов `@` не доходит |
| `replace` + `where: {control_name}` | файл применяется, но правка не действует |
| `replace` + `control_name` и пути с `@` | файл отклоняется целиком |
| Вставка внутрь группы опыта (родители `100%c`) | вся группа и хотбар уезжают |

Экспериментальная попытка получить желаемую раскладку лежит в
`experimental/hud_screen_replace.json` (сборка `Mana_Machines_v1.0.15.mcaddon`):
там те же цели решаются одной операцией `replace` по `control_name`.
**Она с большой вероятностью снова сломает HUD** — тогда удалите паки и
вернитесь к `Mana_Machines_v1.0.14.mcaddon`.

### 16. v1.0.16: полоса в зазоре между хотбаром и полосой опыта

Раз раскладку ванильного HUD сдвинуть нельзя, полосу поставили в свободный
зазор — между хотбаром и полосой опыта:

| Элемент | px от низа экрана |
| --- | --- |
| Хотбар | 8–117 |
| **Полоса маны** | **118.7–128.6** |
| Полоса опыта | 130–154 |
| Цифра уровня | ≈156–182 |
| Сердца и голод | 163–201 |

Зазор всего ≈2.6 UI px, поэтому полоса стала тонкой: `size [200, 2]`

### 17. v1.0.17: мана только в HUD, человеческие названия блоков

**Экшен-бар.** Раз ману показывает полоса в HUD, из строки удалён показатель
`мана/максимум` вместе с индикатором ускоренного восстановления — ускорение
теперь видно по фиолетовому цвету полосы. В экшен-баре остались только
сообщения об ошибках («Недостаточно маны» и похожие), и после последнего
сообщения строка очищается один раз, а не висит на экране.

**Названия блоков.** В руках блоки назывались сырой строкой вида `tile....`.
Причина: переводы лежали с ключами через точки (`tile.mana.condenser.name`),
а игра ищет ключ с двоеточием после пространства имён —
`tile.mana:condenser.name`. Что сделано:

- в `RP/texts/ru_RU.lang` и `en_US.lang` добавлены правильные ключи
  `tile.mana:condenser.name`, `tile.mana:anvil.name`, `tile.mana:fusion.name`;
- в каждый блок добавлен компонент `minecraft:display_name`, который явно
  ссылается на свой ключ;
- старые ключи через точки удалены, чтобы не вводить в заблуждение.

Названия: **Конденсатор маны**, **Блок формирования манакамня**,
**Блок слияния манакамней** (английские — `Mana Condenser`,
`Mana Stone Former`, `Mana Stone Fusion`).

### 18. v1.0.18: предметы на блоках опущены, у наковальни — перед молотом

Координаты посадочных мест — в пикселях модели (16 px = 1 блок), в
`DISPLAY_SEATS` в `main.js`:

| Место | Было (px) | Стало (px) | Что изменилось |
| --- | --- | --- | --- |
| `condenser` | y 8.85 | y 4.05 | ниже на 0.3 блока |

Почему у наковальни сдвиг по `z`: молот (`spectral_hammer`) висит на

`DISPLAY_SEATS` (и версия раскладки, чтобы старые витрины переехали).

### 19. v1.0.19: внешний API маны для других аддонов

Другой аддон может узнать баланс маны, начислить её или списать. Обмен идёт
через **скриптовые события** — это единственный штатный канал между аддонами.

**Почему нельзя просто прочитать значение.** Мана лежит в dynamic property
игрока `mana:value`, но dynamic properties привязаны к UUID бихевиор-пака:
чужой аддон не увидит этот ключ, даже зная его имя, — `getDynamicProperty`
вернёт `undefined`.

#### События

| Событие | Кто шлёт | Сообщение | Что делает | Ответ |
| --- | --- | --- | --- | --- |
| `mana:get` | другой аддон | `{"player":"Steve"}` | — | `mana:balance` |
| `mana:set` | другой аддон | `{"player":"Steve","amount":500}` | ставит значение | `mana:balance` |
| `mana:add` | другой аддон | `{"player":"Steve","amount":100}` | прибавляет | `mana:balance` |
| `mana:spend` | другой аддон | `{"player":"Steve","amount":50}` | списывает, если хватает | `mana:result` |
| `mana:changed` | этот аддон | — (рассылка) | — | — |

Полезная нагрузка ответа — JSON-строка: `{ player, id, max: 1000, mana }`.
`mana:result` добавляет `ok`, `spent`, а при нехватке — `need`. Рассылка
`mana:changed` улетает один раз на каждое изменение: `{ player, id, max, mana, regen }`.

Правила:

- игрока можно указать **по имени** (`player: "Steve"`) или **по id** (`player: "-4293..."`);
  если `player` не передан, берётся тот, кто выполнил команду;
- значения обрезаются до `0…1000` тем же `setMana`, дроби отбрасываются;
- не хватает маны — приходит `ok: false`, баланс **не** меняется;
- ответ приходит в **следующем тике**: API асинхронный, сразу после
  `sendScriptEvent` значения ещё нет;
- чужие события, неизвестные игроки и битый JSON игнорируются молча.

#### Код для второго аддона

```js
import { system, world } from "@minecraft/server";

const balance = new Map(); // id игрока -> мана

// Приёмник: слушаем только неймспейс mana, чтобы не задевать чужие события.
system.afterEvents.scriptEventReceive.subscribe((event) => {
  if (event.id !== "mana:balance" && event.id !== "mana:result" && event.id !== "mana:changed") return;
  let payload;
  try { payload = JSON.parse(event.message); } catch { return; }
  if (typeof payload.mana === "number") balance.set(payload.id ?? payload.player, payload.mana);
  if (event.id === "mana:result" && payload.ok === false) {
    // Маны не хватило: нужно было payload.need, есть payload.mana.
  }
}, { namespaces: ["mana"] });

const send = (id, message) => system.sendScriptEvent(id, JSON.stringify(message));
export const askMana   = (pl) => send("mana:get",   { player: pl.id });
export const spendMana = (pl, n) => send("mana:spend", { player: pl.id, amount: n });
export const addMana   = (pl, n) => send("mana:add",   { player: pl.id, amount: n });
```

Оба пака должны быть включены в один мир. ID события обязан быть с неймспейсом,
но не `minecraft` — поэтому `mana:*` подходит.

#### Ручной вызов из чата

Нужны читы:

```
/scriptevent mana:get {"player":"Steve"}
/scriptevent mana:spend 50
/scriptevent mana:add 25
```

Во второй и третьей форме сообщение — просто число, а игрок берётся из того,
кто выполнил команду.

## Сборка и установка

```bash
python3 build.py
```

Полученный `Mana_Machines_v1.0.19.mcaddon` откройте в Minecraft (двойной клик или
«Открыть с помощью Minecraft»). Старую версию пака перед импортом лучше удалить,
чтобы не было конфликта UUID.

Важно при обновлении:

- сформированные камни из v1.0.4 и раньше останутся в инвентаре, но их уровень
  восстановится только из названия; если один старый стак содержал камни разных
  уровней, уровень будет общим;
- блоки машин, поставленные v1.0.4, можно не переставлять: состояние машин
  сохраняется, витрины обновятся при следующем взаимодействии.

## Проверка

- `node --check src/Mana_Machines_BP/scripts/main.js` — синтаксис JS.
- Скрипт проходит `tsc --checkJs` против официальных типов `@minecraft/server@2.11.0`.
- `node tests/runtime-smoke.mjs` — smoke-тест: регистрация компонента,
  конденсатор, блок слияния, зелье маны, **лимиты уровней по ванильным

  вдалеке, остаток стака, отложенная проверка)** и **посадочные места
  витринных предметов**. Мок `ItemStack` выбрасывает исключение при записи
  динамического свойства в стакуемый предмет — именно так ловится баг уровней.
- Все JSON-файлы валидны, размеры текстур полосы проверяются тестом.
